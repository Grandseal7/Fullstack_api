## ЛР 1–2. HTML, CSS, JS, DOM, Fetch, Git

**Что происходит в `loadProducts()`?**
`fetch()` отправляет HTTP-запрос `GET` на сервер. `await` ждёт ответа, не блокируя страницу. `response.json()` превращает тело ответа из JSON-текста в массив объектов. Затем `renderProducts()` для каждого товара создаёт `<article>` через `document.createElement` и добавляет его в `.catalog`. Карточки строятся из данных, а не из захардкоженного HTML.

**Обработчик клика внутри `forEach`.** Кнопка существует сразу после создания карточки: `card.querySelector('button')` находит её без поиска по всему документу.

## ЛР 3. React

1. **Зачем пустой массив `[]` в `useEffect`?** Эффект выполнится один раз, при первом появлении компонента. Без массива он запускался бы после каждого рендера: `setProducts` вызывает рендер, рендер снова вызывает запрос. Получился бы бесконечный цикл запросов.
2. **Что такое `props`?** Объект с данными, которые родитель передаёт дочернему компоненту: `<ProductCard product={p} />`. Дочерний компонент props только читает.
3. **Controlled input.** Значение поля хранится в state React (`value={searchTerm}`), а `onChange` обновляет state на каждый символ. Источник правды — React, а не DOM. Неуправляемый input хранит значение только в DOM.
4. **`key`** помогает React отличать элементы списка при перерисовке.
5. **Lifting state up.** Счётчик корзины — общие данные, поэтому он хранится в общем родителе `App`. Карточки только сообщают о клике через функцию-prop `onAdd`.

## ЛР 4. Вёрстка

**Отчёт:**
- Box model карточки: content ___, padding 16px, border 1px, margin 0. Без `border-box` итоговая ширина = width + 2×16 + 2×1. С `border-box` итоговая ширина = width.
- `repeat(4, 1fr)` на 500px: четыре колонки сжимаются, карточки становятся очень узкими, текст и картинки ломаются.
- `auto-fit` против `auto-fill`: при 1–2 товарах `auto-fit` схлопывает пустые колонки и растягивает карточки на всю ширину. `auto-fill` оставляет пустые колонки, и карточки сохраняют ширину около 220px.

| Ширина | Колонок | «Доставка» | Шапка |
|---|---|---|---|
| 375 px | 1 | под каталогом | столбик |
| 768 px | 2–3 | под каталогом | ряд |
| 1280 px | 3–4 | справа | ряд |

**Вопросы:**
1. `<section>` — тематический раздел страницы. `<article>` — самостоятельный фрагмент, который имеет смысл и вне страницы. Карточка товара самостоятельна, поэтому это `<article>`.
2. `<main>` — основное, уникальное содержимое страницы, поэтому он один. Разделов `<section>` может быть сколько угодно.
3. С `border-box` `width` включает padding и border. Без него padding и border прибавляются к `width`, и карточка становится шире заданной.
4. Шапка — один ряд элементов, это одномерная задача для Flexbox. Каталог — строки и колонки, это двумерная задача для Grid.
5. `repeat(auto-fit, minmax(220px, 1fr))`: столько колонок, сколько влезет, каждая не уже 220px, свободное место делится поровну.
6. Mobile-first: базовые стили пишем для телефона, большие экраны «достраиваем» через `min-width`. `min-width` значит «от этой ширины и больше».
7. `<label htmlFor>` связывает подпись с полем: клик по подписи ставит курсор в поле, скринридер читает подпись. `type="email"` проверяет формат и открывает клавиатуру с `@` на телефоне.

## ЛР 5–6. Express, REST API

**Отчёт:**
- `Content-Type`: `res.send('строка')` → `text/html; charset=utf-8`, `res.json()` → `application/json; charset=utf-8`.
- Без `next()` в middleware запрос «висит»: ответ не отправлен, а дальше по цепочке запрос не передан. Браузер крутит загрузку до таймаута.
- Логгер после маршрутов не логирует `/api/products`: маршрут уже отправил ответ и не вызвал `next()`, до логгера запрос не дошёл.
- Без `express.json()` `req.body` = `undefined`. Сервер отвечает `400`: обязательные поля «не пришли».

**Вопросы:**
1. `json-server` — готовый фейковый сервер по JSON-файлу. Наш Express-сервер — свой код: валидация, логика, доступ, база данных.
2. `req` — запрос: `req.params`, `req.query`, `req.body`, `req.headers`, `req.method`. `res` — ответ: `res.status()`, `res.json()`, `res.send()`.
3. `req.params` — часть пути: `/api/products/2` → `id = '2'`. `req.query` — строка запроса: `/api/products?search=мёд`. `req.body` — тело POST/PUT: `{ "name": "Сыр" }`.
4. Middleware — функция `(req, res, next)`, звено конвейера до обработчика. Без `next()` запрос зависает.
5. `app.use()` выполняется по порядку. Обработчик 404 — последний, после всех маршрутов: туда доходят только неподошедшие запросы.
6. Origin = протокол + домен + порт. `localhost:5173` и `localhost:3000` — разные источники. Браузер по same-origin policy не отдаёт ответ коду страницы без заголовка `Access-Control-Allow-Origin`.
7. HTML5-проверку легко обойти через DevTools, `curl` или Postman. Сервер никогда не доверяет клиенту.
8. `200` OK — `GET /api/products`; `201` Created — `POST /api/orders`; `400` Bad Request — заявка на 5 кг; `404` Not Found — `GET /api/products/999`. Ещё `204` No Content — `DELETE` без тела ответа.
9. REST: ресурс называется существительным в URL (`/api/products`), действие задаёт HTTP-метод (GET, POST, PUT, DELETE). Поэтому не `/getAllProducts`.

## ЛР 7–8. Пользователи, bcrypt, JWT

**Отчёт:**
- Хэши у двух пользователей с одним паролем разные: bcrypt добавляет случайную соль.
- Регистрация с `"role": "admin"` даёт роль `buyer`: роль из тела не читается.
- Подделанный на jwt.io токен не прошёл: подпись считается от заголовка и данных с `JWT_SECRET`. После изменения `role` подпись не сходится, `jwt.verify` бросает ошибку → `401`.
- После порчи токена в `localStorage`: `GET /auth/me` → `401` → `apiFetch` удалил токен и перезагрузил страницу. Пользователь вышел.
- Спрятать кнопку недостаточно: запрос можно отправить из Console или `curl`. Сервер ответил `403` — защита работает на сервере.

**Вопросы:**
1. Аутентификация — «кто вы?», ошибка `401`. Авторизация — «что вам можно?», ошибка `403`.
2. Хэш односторонний, и при утечке базы пароли не узнать. Зашифрованный пароль можно расшифровать ключом. Соль — случайная добавка: одинаковые пароли дают разные хэши, готовые таблицы «пароль → хэш» не работают. bcrypt медленный специально, чтобы перебор миллиардов паролей занял годы.
3. JWT = заголовок . данные . подпись. Первые две части — Base64URL, их читает любой. Поэтому в токене нет пароля, номера карты и других секретов.
4. Без `JWT_SECRET` правильную подпись не посчитать. Если секрет утечёт, злоумышленник выпустит токен админа. Нужно сменить секрет: все старые токены станут недействительны.
5. `requireAuth` проверяет заголовок `Bearer`, подпись и срок, кладёт `req.user`. `requireRole(...roles)` — фабрика: возвращает middleware, настроенный на нужные роли.
6. Одинаковый текст ошибки не позволяет перебором узнать, какие e-mail зарегистрированы.
7. Mass assignment — запись в базу всех полей из тела запроса, включая `role`. Защита: регистрация берёт только `name`, `email`, `password`, а zod отбрасывает лишние поля (`routes/auth.js`, `validate(registerSchema)`).
8. Токен лежит в `localStorage`, `apiFetch` добавляет `Authorization: Bearer`. При выходе токен удаляется. Недостаток: при XSS чужой скрипт прочитает токен. Надёжнее cookie `httpOnly`.
9. Скрытая кнопка — только интерфейс. Настоящая защита — `requireRole` на сервере.
10. Preflight — запрос `OPTIONS` «можно ли?». Браузер шлёт его перед «непростым» запросом (заголовок `Authorization`, `Content-Type: application/json`) на другой origin.

## ЛР 9–10. Деплой и CI/CD

**Отчёт:**
- Предохранитель `db/seed.js` на Neon: «Отказ: db:init запущен НЕ на локальной базе — все данные будут удалены». Он защищает продакшен от случайного стирания.
- Каталог на Vercel сначала не загрузился: адреса Vercel не было в `CORS_ORIGIN`. Добавили точный origin без `/` на конце.
- В PR job `deploy` — `skipped` из-за условия `if: push в main`. На Preview Vercel каталог не работает: адреса Preview нет в `CORS_ORIGIN`.
- Время конвейера Merge → smoke: ___ мин.
- При `JWT_SECRET=123` новая версия не стартовала, а старая продолжала работать (zero-downtime: трафик переключается после health check).
- Ночью при аварии — Rollback на Render. Утром — `git revert` через PR, чтобы `main` снова совпадал с продакшеном.
- Холодный старт: первый ответ ___ с, повторный ___ мс. Бесплатный Render засыпает через 15 минут простоя, Neon — через 5 минут.

**Вопросы:**
1. React — Vercel (CDN), Express — Render, PostgreSQL — Neon. Сервер и база в одном регионе (Frankfurt): каждый запрос к API делает несколько запросов к базе, и большие расстояния замедлили бы сайт.
2. Переменные Render читаются при запуске через `process.env` и видны только серверу. `VITE_` подставляются при сборке в JS, их видит любой посетитель. Поэтому в `VITE_` нет секретов.
3. `db:init` удаляет все таблицы. Миграция создаёт только недостающее. Идемпотентность: повторный запуск даёт тот же результат.
4. CORS: сервер разрешил чтение ответа только origin из `CORS_ORIGIN`. Исправили, добавив адрес Vercel.
5. `trust proxy`: за балансировщиком `req.ip` берётся из `X-Forwarded-For`. Без него у всех пользователей был бы IP прокси и один общий лимит попыток входа.
6. Merge → `test` → (`needs: test`) `deploy`: deploy hook с `ref=SHA` разворачивает ровно проверенный коммит, затем smoke. `if` запрещает деплой из PR. Deploy hook — секрет: по нему любой запустит деплой.
7. Smoke-тест — быстрые проверки живого продакшена после деплоя. Он ничего не создаёт и не удаляет, потому что в базе настоящие данные.
8. Текст ошибки `500` раскрывает устройство сервера (адрес базы, SQL). Ошибка `400` — про данные клиента, её текст полезен и безопасен.
9. При `SIGTERM` сервер закрывает приём новых соединений, ждёт текущие запросы и закрывает пул базы. Падать при неверной конфигурации нужно сразу: так деплой не пройдёт health check и старая версия продолжит работать.
10. Сервер засыпает через 15 минут простоя. Первый запрос будит его около минуты, пользователь видит баннер «Сервер просыпается…».
11. Rollback — минута, но без тестов и без изменения истории Git. `git revert` — полный конвейер, и `main` = продакшен. Ночью — Rollback, утром — revert.
12. После смены `JWT_SECRET` все выданные токены станут недействительны (`401`), пользователям нужно войти заново.
13. `npm ci` ставит строго по `package-lock.json`, удаляет `node_modules` и падает при расхождении с `package.json`. Сборка воспроизводима.
14. CI — автоматическая сборка и тесты каждого изменения (job `test`). CD — автоматическая выкладка прошедшей версии (job `deploy` + Vercel).
15. `.env` не хранят в репозитории: секреты из Git утекают навсегда, а у каждой среды свои значения.

## ЛР 12. Docker

**Отчёт:**
- Размеры образов: `node:20-alpine` ≈ ___ МБ, `agromarket-web:local` ≈ ___ МБ.
- После `docker compose down` и `up` админ и новый товар на месте: данные лежат в именованном volume `pgdata`, который `down` не удаляет. `down -v` удаляет volume, и при следующем старте `api` миграция заново создаёт таблицы, товары из `data/db.json` и админа.

**Вопросы:**
1. Образ — неизменяемый шаблон (файлы + команда запуска). Контейнер — запущенный экземпляр образа. Из одного образа можно запустить сколько угодно контейнеров.
2. Слой `npm ci` кешируется, пока не изменился `package*.json`. Правка кода пересобирает только слой `COPY . .`.
3. Multi-stage: Node нужен только для сборки. В финальный образ попадают `dist/` и Nginx: около 50 МБ вместо 500+ МБ.
4. Volume — хранилище вне контейнера. `down` сохраняет данные, `down -v` их удаляет.
5. Внутри контейнера `localhost` — это сам контейнер `api`. Базу находят по имени сервиса `db` во внутренней сети Compose.
6. `healthcheck` проверяет `pg_isready`. `condition: service_healthy` запускает `api`, только когда база готова принимать соединения.

## Итоговый вопрос: что удалось и что бы я сделал иначе

Самое удачное решение — слоистая архитектура сервера (routes / middleware / validation / db) и единая схема `schema.sql`. Одну и ту же схему используют `db:init`, миграция и Docker. Иначе я бы сделал так: сразу TypeScript, общие zod-схемы для клиента и сервера, токен в cookie `httpOnly` вместо `localStorage` и инструмент миграций с версиями (`node-pg-migrate`).
